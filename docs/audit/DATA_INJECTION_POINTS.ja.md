# 信号へのデータ注入の検討

[English](DATA_INJECTION_POINTS.md)

2026-09-09、`codex/interactive-guide-thermal-inputs` のコード監査。今回は注入機能の実装ではなく、実装余地と設計上の条件を整理した。

**画像・ノイズ・過去フレームを混ぜる余地はある。最初はDATAまたはCOLORの直後に、固定画像かシード付きノイズを注入する構成が適する。** 現在のGPUパスは入力テクスチャが1つだけで、入力追加の仕組みはない。STREAM ERRORも現在の入力を再サンプリングする処理であり、本物の過去フレームは参照していない。`Frame.through(point)` は処理の途中までを選ぶ関数で、入力用のフックではない。

| 注入位置 | 混ぜられるもの／用途 | 留意点 |
| --- | --- | --- |
| SENSORの前 | 画像への置換、ノイズ源 | カメラ外部テクスチャと通常画像の向き・縦横比を統一 |
| SENSOR | 露光むら、欠損画素マスク | RGB近似とRAWセンサー値を区別 |
| READOUT | 行単位のずれ・置換 | RAWではBayer配列の位相を維持 |
| DATA | ビットマスク、ノイズ、画像断片 | 初期実験に向く。BIT/ADDRESS処理の後など順序を明示 |
| RECONSTRUCTION | CFAデータ、別フレームのモザイク | RGBとRAWで別の変換が必要 |
| COLOR | 画像ブレンド、パレット・ノイズ | 効果が理解しやすく、固定画像注入の第一候補 |
| STREAM | 遅延フレーム、ブロック置換 | 専用の過去フレーム保持が必要 |
| MEDIA | フィードバック、テープ欠損マスク | VHSの前後どちらかを明示 |
| DISPLAY | 別画像による走査線・発光変化 | CRT前後。保存対象の信号内で処理する |

対象FAULTがOFFでも注入位置を有効にできる設計が必要。選択中のFAULTを回すループ内にだけ追加すると、そのFAULTが未選択のとき注入が消えてしまう。

## 最初の実装案

注入スロットは1つ。固定画像または手続き的ノイズを、DATAかCOLORの直後で混ぜる。画像は寸法を制限して一度だけ読み込み・GPUへ転送する。毎フレームのCPU読み戻しは避け、2入力のシェーダーで混ぜる。OFF時は既存出力を完全に維持する。

注入元の識別子、位置、混合方式、量、拡大・切り取り、乱数シード、時刻を変更不能な撮影状態に含める。画面表示だけに重ねず、プレビュー・JPEG・動画が共有する処理済みバッファへ入れる。撮影中に画像を差し替えても、確定した撮影が使う古い画像と状態を保持する。

追加テクスチャと通常1回の全画面処理が必要になる。RGBA8は1920×1080で約7.91 MiB、3072×4096で48 MiB／枚（ドライバー分は別）。発熱改善とは逆方向の負荷になるため、自動負荷調整に追加パスを算入し、高解像度を初期値にしない。新しい依存ライブラリや通信サービスは不要。

## 次の段階

過去フレームは専用の1〜2枚のGPUバッファで保持する。注入前を残すか注入後を残すか、フレーム間引き時の遅延、リサイズ・一時停止時のリセットを定義する。既存の`FrameHistory`は表示済み画像と撮影予約を守るためのものなので、書き換え可能なフィードバック用に流用しない。同じテクスチャへの読み書きを同一描画で行わない。

RAWへの注入は別工程。`RawGlitch.chain`のRAW16サンプルに合わせ、黒・白レベルとCFA配列へ変換する。RGBのバイト列をそのまま流し込まない。意図したCFA破壊を除き配列位相を維持し、DNGのヘッダーやメタデータを壊さない。RGBプレビューとRAW出力の違いは引き続き明示する。

実装時には、OFF時の既存画像との一致、同じシードでの再現性、撮影中の画像交換、プレビューと保存の状態一致、RAW境界、メモリ上限、追加GPU負荷を検証する。詳細なコード位置と受け入れ条件は英語版に記載した。
